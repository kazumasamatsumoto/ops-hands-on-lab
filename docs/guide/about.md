# このラボについて

::: tip 3 行まとめ
- アプリを「作る」だけでなく「動かし続ける」ために必要なことを、実物を触って覚えるための練習場です。
- やっていることは特別な技術ではありません。**開発と運用に必要なことを、抜けなく並べて、1 つずつ確かめているだけ**です。ただ、それをきちんとやった経験のある人が少ないので、知らない言葉に見えます。
- 順番は **触る(演習)→ 仕組みを知る → 一覧で穴を知る → 設計書に書く** です。構成は SAP Commerce Cloud(CCv2)でヘッドレスのお店を動かすときの形に寄せているので、覚えたことが実案件の構成図や API の URL にそのまま重なります。
:::

## 1. こんな人のためのラボです

SIer で、画面や API を作る仕事をしてきた人を思い浮かべて作りました。たとえば次のような経験があるかもしれません。

- 性能は「負荷試験の結果表を最後に貼る」ものだった。
- セキュリティは「脆弱性診断の会社が指摘をくれる」ものだった。
- 運用は「リリースしたら運用チームに手順書を渡して終わり」だった。
- インフラは「基盤チームがサーバーを用意してくれる」ものだった。

それで何も悪くありません。分業の中で、自分の担当をきちんとこなしてきたということです。
ただ、クラウドで動かし、頻繁にリリースし、インターネットにそのまま出すようになると、**この「分業の外側」にあった仕事が、開発チームの手元に戻ってきます**。
方式設計書に SLO、WAF、CDN、SSR、ローリング更新といった言葉が並ぶのはそのためです。

## 2. つまずきは 3 つあります

設計書を読んで「分からない」と感じるとき、原因はたいてい次の 3 つのどれかです。

| つまずき | 心の声 | このラボの答え方 |
| --- | --- | --- |
| **なぜ必要か分からない** | 「この文書、無くても作れるのでは?」 | 無いときに起きる事故を、演習で**自分で起こして**見ます。例: キャッシュの設定を間違えると、他人の画面が見える |
| **何をやっているか分からない** | 「バーンレート? 何を計算しているの?」 | 設定ファイルを 1 行ずつ読める形で置き、数字が動く様子を画面(Grafana)で見ます |
| **単語が分からない** | 「SSR、WAF、SLO… 略語ばかり」 | 演習の中で出てきた順に「一言でいうと」と「たとえ」を付けます。[用語集](/guide/glossary)にもまとめています |

どれも頭の良し悪しの問題ではありません。**やったことが無いから知らない**、それだけです。
一度手を動かすと、「なんだ、そういうことか」となるものがほとんどです。

## 3. 触る → 仕組みを知る → 一覧で穴を知る → 設計書に書く

このラボは、次の順番で使うように作っています。

```text
① 触る(演習)            自分の PC で動かし、スイッチでわざと壊し、数字や画面で確かめる
        ↓
② 仕組みを知る(仕組み)   いま触った部品が、中でどう動いているかを 1 リクエストの流れと設定の 1 行ずつで知る
        ↓
③ 一覧で穴を知る(一覧)   それが「開発・運用に必要なこと一覧」のどの行か、自分の案件で抜けていないかを確かめる
        ↓
④ 設計書に書く(設計書)   設計書のどの節に、何を書けばよいかを知る。ラボ自身の設計書を見本として読む
```

- **① 触る**: [演習](/exercises/01-fe-ssr-vs-csr)は 21 本あり、10 の分野(FE・BE・インフラ・ネットワーク・SRE・QA・性能・障害対応・DR・セキュリティ)とヘッドレスに分かれています。どのページも「なぜ必要か → 何をやっているか → 触ってみる → 何が見えたら成功か → 言葉 → 設計書ではここに書く → レビューで聞く質問 → 片付け」の同じ形です。
- **② 仕組みを知る**: [仕組み](/how-it-works/00-overview)は、部品ごとの説明です。cdn-waf(CDN と WAF の役)、ingress(エンドポイントと IP フィルタ)、storefront の SSR と CMS 駆動の描画、api(OCC 風の API)、OAuth のトークン、worker の定期ジョブ、検索(Solr)、観測(指標・ログ・トレース)、manifest と環境(d1・s1・p1)などを、**1 リクエストの流れ・設定の各行の意味・確かめるコマンド・CCv2 ではどこに当たるか・よくある誤解** の順で説明します。演習で「動いた」を見たあとに読むと、「なぜそう動いたか」が分かります。
- **③ 一覧で穴を知る**: [開発・運用に必要なこと一覧](/guide/checklist)が、このラボの中心のページです。アプリを作って動かし続けるのに要ることを 1 行ずつ並べ、「無いとどんな事故が起きるか」を書いています。ラボで扱っていない項目(権限の棚卸し、当番表、証明書の期限など)も入れています。自分の案件で空いている行が、次に手を付ける場所です。
- **④ 設計書に書く**: [ラボの設計書](/design/architecture/00-overall)は、このラボ自身の方式設計書と詳細設計書です。書いてある値(SSR のタイムアウト 3000ms、キャッシュ 30 秒、ログインの回数制限 1 秒 1 回、SLO 99.9% など)は、すべて実物の設定ファイルと同じで、ファイルへのリンクが付いています。「設計書の値」と「動いている物の値」がつながっていることを確かめられます。

迷ったら [地図](/guide/map) を開いてください。ラボのどの部品が、どの設計書の、どの分野に関係するか、CCv2 では何に当たるかを 1 枚にしています。
SIer でなじみのある言葉(基本設計、結合試験、運用設計書など)との対応は [SIer の言葉との対応表](/guide/sier-mapping) にあります。

### ラボの形は CCv2 + ヘッドレスに合わせています

ラボの部品は、SAP Commerce Cloud(CCv2)で画面と API を分けた作り(ヘッドレス。Composable Storefront を使う形)のお店を動かすときの部品と、1 対 1 で対応させています。

| ラボ | CCv2 で当たるもの |
| --- | --- |
| cdn-waf | お客さんが別に契約する CDN と WAF |
| ingress のホスト名ごとの振り分け(www・api・backoffice) | Cloud Portal の「エンドポイント」 |
| ingress の IP 制限 | エンドポイントの「IP フィルタ」 |
| storefront(Angular SSR) | JS Storefront(SSR) |
| api の `/occ/v2/samplestore/...` | OCC の REST API |
| api・backoffice・worker を `ASPECT` で切り替える | aspect(api・backoffice・backgroundProcessing) |
| `manifest.json` と `tools/manifest/render.mjs` | manifest.json とビルド |
| 本格版の環境 d1・s1・p1 | 環境 d1・s1・p1 |

全部の対応は [地図の「CCv2 との対応」](/guide/map#ccv2) にあります。ラボで「ホスト名で振り分けて、backoffice だけ IP で絞る」を触っておくと、実案件で Cloud Portal のエンドポイントの画面を見たときに、何を決める画面なのかがすぐ分かります。

## 4. 準備

Docker Desktop(メモリ 8GB 割り当て)があれば動きます。手順は [準備と起動](/guide/setup) を見てください。
軽量版(docker compose だけ)で、ほとんどの演習ができます。本格版(kind = Docker の中の Kubernetes)は、ローリング更新や台数を増やす演習、検索の Solr、トレース(1 リクエストの道筋)、環境 d1・s1・p1 の違いを見るときに使います。
お店の画面は http://www.lab.localhost:18080 、API は http://api.lab.localhost:18080 、管理画面は http://backoffice.lab.localhost:18080/backoffice/ で開きます(どちらの版でも同じ)。

## 5. チームで使うときの進め方(例)

1 人で読み進めても使えますが、チームで少しずつ進めると定着しやすくなります。

| 進め方 | やること | 時間の目安 |
| --- | --- | --- |
| **週に 1 演習** | 担当を 1 人決め、演習ページの手順を画面共有しながらやってみせる | 30〜45 分 |
| **仕組みを 1 本読む** | 演習で触った部品の [仕組み](/how-it-works/00-overview) のページを読み、「確かめるコマンド」を 1 つ打ってみる | 10 分 |
| **質問を読み上げる** | 各演習の最後の「レビューで聞く質問」を、全員でそのまま読み上げて答えてみる。答えられなかった質問はメモする | 10 分 |
| **自分の案件に当てはめる** | [必要なこと一覧](/guide/checklist) の該当する行を開き、「自分の案件でできているか」に印を付ける | 10 分 |
| **設計書を 1 節読む** | その演習に対応するラボの設計書の節を読み、「自分の案件の設計書ならどこに書くか」を話す | 10 分 |

21 本あるので、週 1 本なら約 5 か月です。全部やる必要はありません。自分の案件で弱い分野から選んでください。

::: info おすすめの順番
最初の 5 本は [SSR と CSR](/exercises/01-fe-ssr-vs-csr) → [CMS の JSON が画面になるまで](/exercises/21-headless-cms) → [Ingress とエンドポイント](/exercises/20-nw-ingress-endpoints) → [前段のキャッシュ](/exercises/07-nw-cache) → [API が遅い → SSR が逃げる](/exercises/14-incident-slow-api) がおすすめです。
画面・ヘッドレスの作り・入口・障害が 1 本の線でつながり、「なぜ全部の分野が要るのか」が見えやすくなります。続けて [SLI と SLO](/exercises/09-sre-sli-slo) で見張りを足してください。
:::

## 6. 約束ごと

- 題材は架空のネットストア「サンプルストア」(サンプル株式会社)です。データもすべて架空です。
- パスワードは、わざと分かりやすい見本の値にしています(会員 `alice` / `password`、管理画面 `admin` / `admin` など)。本番では同じことをしません。
- 攻撃の見本のスクリプトは、**このラボ(http://www.lab.localhost:18080 と http://api.lab.localhost:18080)にだけ**使ってください。実在のサイトに送ってはいけません。
- SAP の資料の文章は載せていません。CCv2 との対応は「ラボのこれは、CCv2 ではこれに当たる」という呼び方の対応だけです。
- すべて自分の PC の中で動きます。外部のサービスには何も送りません。
