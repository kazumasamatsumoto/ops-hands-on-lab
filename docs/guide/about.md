# このラボについて

::: tip 3 行まとめ
- アプリを「作る」だけでなく「動かし続ける」ために必要なことを、実物を触って覚えるための練習場です。
- やっていることは特別な技術ではありません。**開発と運用に必要なことを、抜けなく並べて、1 つずつ確かめているだけ**です。ただ、それをきちんとやった経験のある人が少ないので、知らない言葉に見えます。
- 順番は **触る(演習)→ 知る(一覧・用語集)→ 書く(設計書)** です。
:::

## 1. こんな人のためのラボです

SIer で、画面や API を作る仕事をしてきた人を思い浮かべて作りました。たとえば次のような経験があるかもしれません。

- 性能は「負荷試験の結果表を最後に貼る」ものだった。
- セキュリティは「脆弱性診断の会社が指摘をくれる」ものだった。
- 運用は「リリースしたら運用チームに手順書を渡して終わり」だった。
- インフラは「基盤チームがサーバーを用意してくれる」ものだった。

それで何も悪くありません。分業の中で、自分の担当をきちんとこなしてきたということです。
ただ、クラウドで動かし、頻繁にリリースし、インターネットにそのまま出すようになると、**この「分業の外側」にあった仕事が、開発チームの手元に戻ってきます**。
方式設計書に SLO、WAF、CDN、SSR、ローリング更新といった言葉が並ぶのはそのためです。

## 2. つまずきは 3 つあります

設計書を読んで「分からない」と感じるとき、原因はたいてい次の 3 つのどれかです。

| つまずき | 心の声 | このラボの答え方 |
| --- | --- | --- |
| **なぜ必要か分からない** | 「この文書、無くても作れるのでは?」 | 無いときに起きる事故を、演習で**自分で起こして**見ます。例: キャッシュの設定を間違えると、他人の画面が見える |
| **何をやっているか分からない** | 「バーンレート? 何を計算しているの?」 | 設定ファイルを 1 行ずつ読める形で置き、数字が動く様子を画面(Grafana)で見ます |
| **単語が分からない** | 「SSR、WAF、SLO… 略語ばかり」 | 演習の中で出てきた順に「一言でいうと」と「たとえ」を付けます。[用語集](/guide/glossary)にもまとめています |

どれも頭の良し悪しの問題ではありません。**やったことが無いから知らない**、それだけです。
一度手を動かすと、「なんだ、そういうことか」となるものがほとんどです。

## 3. 触る → 知る → 書く

このラボは、次の順番で使うように作っています。

```text
① 触る(演習)       自分の PC で動かし、スイッチでわざと壊し、数字や画面で確かめる
        ↓
② 知る(一覧・用語集)  いま触ったものが「開発・運用に必要なこと一覧」のどの行か、言葉の意味は何かを確かめる
        ↓
③ 書く(設計書)       設計書のどの節に、何を書けばよいかを知る。ラボ自身の設計書を見本として読む
```

- **① 触る**: [演習](/exercises/01-fe-ssr-vs-csr)は 19 本あり、10 の分野(FE・BE・インフラ・ネットワーク・SRE・QA・性能・障害対応・DR・セキュリティ)に分かれています。どのページも「なぜ必要か → 何をやっているか → 触ってみる → 何が見えたら成功か → 言葉 → 設計書ではここに書く → レビューで聞く質問 → 片付け」の同じ形です。
- **② 知る**: [開発・運用に必要なこと一覧](/guide/checklist)が、このラボの中心のページです。アプリを作って動かし続けるのに要ることを 1 行ずつ並べ、「無いとどんな事故が起きるか」を書いています。ラボで扱っていない項目(権限の棚卸し、当番表、証明書の期限など)も入れています。
- **③ 書く**: [ラボの設計書](/design/architecture/00-overall)は、このラボ自身の方式設計書と詳細設計書です。書いてある値(タイムアウト 3000ms、キャッシュ 30 秒、SLO 99.9% など)は、すべて実物の設定ファイルと同じで、ファイルへのリンクが付いています。「設計書の値」と「動いている物の値」がつながっていることを確かめられます。

迷ったら [地図](/guide/map) を開いてください。ラボのどの部品が、どの設計書の、どの分野に関係するかを 1 枚にしています。
SIer でなじみのある言葉(基本設計、結合試験、運用設計書など)との対応は [SIer の言葉との対応表](/guide/sier-mapping) にあります。

## 4. 準備

Docker Desktop(メモリ 8GB 割り当て)があれば動きます。手順は [準備と起動](/guide/setup) を見てください。
軽量版(docker compose だけ)で、ほとんどの演習ができます。本格版(kind = Docker の中の Kubernetes)は、ローリング更新や台数を増やす演習で使います。

## 5. チームで使うときの進め方(例)

1 人で読み進めても使えますが、チームで少しずつ進めると定着しやすくなります。

| 進め方 | やること | 時間の目安 |
| --- | --- | --- |
| **週に 1 演習** | 担当を 1 人決め、演習ページの手順を画面共有しながらやってみせる | 30〜45 分 |
| **質問を読み上げる** | 各演習の最後の「レビューで聞く質問」を、全員でそのまま読み上げて答えてみる。答えられなかった質問はメモする | 10 分 |
| **自分の案件に当てはめる** | [必要なこと一覧](/guide/checklist) の該当する行を開き、「自分の案件でできているか」に印を付ける | 10 分 |
| **設計書を 1 節読む** | その演習に対応するラボの設計書の節を読み、「自分の案件の設計書ならどこに書くか」を話す | 10 分 |

19 本あるので、週 1 本なら約 5 か月です。全部やる必要はありません。自分の案件で弱い分野から選んでください。

::: info おすすめの順番
最初の 4 本は [SSR と CSR](/exercises/01-fe-ssr-vs-csr) → [前段のキャッシュ](/exercises/07-nw-cache) → [SLI と SLO](/exercises/09-sre-sli-slo) → [API が遅い → SSR が逃げる](/exercises/14-incident-slow-api) がおすすめです。
画面・入口・見張り・障害が 1 本の線でつながり、「なぜ全部の分野が要るのか」が見えやすくなります。
:::

## 6. 約束ごと

- 題材は架空のネットストア「サンプルストア」(サンプル株式会社)です。データもすべて架空です。
- パスワードや署名鍵は、わざと分かりやすい見本の値にしています。本番では同じことをしません。
- 攻撃の見本のスクリプトは、**このラボ(http://localhost:18080)にだけ**使ってください。実在のサイトに送ってはいけません。
- すべて自分の PC の中で動きます。外部のサービスには何も送りません。
