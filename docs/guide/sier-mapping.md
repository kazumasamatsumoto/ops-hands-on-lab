# SIer の言葉との対応表

::: tip 3 行まとめ
- このラボの言葉の多くは、SIer の文書にもともとある考え方の「言い換え」か「細かくしたもの」です。まったく新しいものは意外と少ないです。
- 新しく見えるものが増えた理由は 3 つです。**クラウドで動かす**、**何度もリリースする**、**インターネットにそのまま出す**。
- 対応が分かれば、「うちの案件ではどの文書のどこに書くか」が決まります。ラボは CCv2 + ヘッドレスの形なので、CCv2 の案件で出てくる言葉(エンドポイント、aspect、OCC、manifest、d1/s1/p1 など)との対応も第 3 章にまとめました。
:::

## 1. まず全体の対応

左が SIer でなじみのある文書や工程、右がこのラボ(と、クラウドの案件の設計書)で出てくる言葉です。

| SIer の言葉 | このラボの言葉 | 同じところ | 違うところ・増えたところ |
| --- | --- | --- | --- |
| 要件定義・非機能要求グレード | SLO(サービス目標)、RTO・RPO、性能目標 | 「どれくらい止まってよいか」「どれくらい速いか」を先に決める | 目標を**数式で**決め、**本番で毎日測る**。例: 99.9% → 1 か月で約 43.2 分まで失敗してよい |
| 基本設計・方式設計 | 方式設計書(全体・FE・BE・インフラ・ネットワーク・SRE・QA・性能・障害対応・DR・セキュリティ) | 層ごとに方針を決め、理由を残す | 分野が 10 に分かれ、SRE・セキュリティ・DR が独立した文書になる |
| 詳細設計 | 詳細設計書(画面 1 つ、API 1 つ、監視項目 1 つ、障害シナリオ 1 つ…) | 1 つの物をどう作るかを決める | 「監視項目 1 つ」「障害 1 つ」のように、**運用の物も詳細設計の単位になる** |
| 方式設計の「システム構成図」 | 構成図(ブラウザ → CDN・WAF → エンドポイント → storefront / api / backoffice / worker → DB・検索) | 箱と線で全体を示す | 前段(CDN・WAF)、入口の振り分け(エンドポイント)、観測(指標・ログ・トレース・アラート)の箱が増える |
| 画面設計 | SSR / CSR、ハイドレーション、遅延読み込み、CMS 駆動の描画 | 画面の項目と動き | 「どこで HTML を作るか」「最初に何 KB の JS を読むか」まで決める。ヘッドレスでは**画面の並びを CMS のデータが決める**ので、画面設計は「部品(typeCode)の一覧」と「どのスロットに何を置けるか」になる |
| 画面項目定義・コンテンツの運用ルール | CMS のページ・スロット・部品(typeCode)、backoffice | 画面に何を出すかを決める | 文言やバナーの差し替えは**リリースではなくデータの変更**。キャッシュが切れるまで反映が遅れることを業務側と決めておく |
| インターフェース設計書(外部 IF) | OCC 風 API(`/occ/v2/samplestore/...`)、`fields`、エラーの形 `{errors:[{type,message}]}` | 入出力の項目と形を決める | URL にお店の ID(baseSiteId)が入る。返す量を `fields` で呼び出し側が選ぶ |
| 認証方式設計(ログイン・セッション) | OAuth(パスワードグラント)、公開クライアント、アクセストークン(15 分) | 本人確認と有効期限 | サーバーのセッションではなく**トークン**を毎回見せる。ブラウザのアプリは秘密の鍵を持てない(公開クライアント)。なお、パスワードグラントは学習用の選択で、今の OAuth の指針では使わず、SAP Commerce Cloud の公開クライアントは「認可コード + PKCE」を使うのが標準 |
| バッチ設計書・ジョブ一覧 | 定期ジョブ(CronJob)、backgroundProcessing の aspect、`CronJobStale` アラート | いつ何を動かすかを決める | 専用の台(aspect)で動かし、**最後に成功した時刻**で見張る |
| 検索設計(全文検索・インデックス) | Solr、索引、CJK バイグラム、`searchIndexJob` | 探し方と索引の作り方 | 索引は DB から作り直せる「写し」。反映の遅れ(最大 60 秒)と、作り直しの失敗の見張りを決める |
| 単体試験・結合試験 | 単体テスト・API の結合テスト | 部品ごと・つないだときの確認 | 自動で何度でも流す(リリースのたびに) |
| 総合試験・受入試験 | E2E テスト(Playwright)、画面比較 | 利用者の操作の流れで確かめる | 人が画面を見る代わりに、**ロボットが毎回同じ操作をして画像を比べる** |
| 負荷試験・性能試験 | 負荷試験(k6)、p95、スループット、スケールアウト | 何人まで耐えるかを確かめる | 一度きりでなく、**限界点と「どこが先に詰まるか」**を見る。台数を増やして耐える方法もセット |
| 運用設計書 | SRE 方式設計書、監視項目、アラート、ダッシュボード | 何を見張り、誰が動くかを決める | 「CPU 80%」ではなく**利用者から見た成功率・速さ**で見張る。鳴らす基準を数式で決める |
| 監視設計(死活監視・閾値監視) | SLI、バーンレートのアラート、ヘルスチェック(healthz / readyz) | 異常に気づく仕組み | 「生きているか」と「仕事を受けられるか」を分ける。予算の減る速さで鳴らす |
| 障害対応手順書・運用手順書 | ランブック、一次対応、フォールバック、オンコール | 起きたら何をするかを書いておく | 先に**壊れ方を決めておく**(例: API が遅ければ空の画面を返して逃げる) |
| 障害報告書 | ポストモーテム(振り返り) | 原因と再発防止を残す | 「誰が悪いか」ではなく「仕組みのどこを変えるか」に集中する |
| 保守・運用体制表 | 当番表(オンコール)、通知経路(pager) | 誰に連絡が行くか | 夜中も含めて**機械が人を呼ぶ**。緊急と翌営業日を分ける |
| バックアップ設計・BCP | DR 方式、RTO・RPO、バックアップと復元の訓練 | データを失わない、止まっても戻す | **戻せることを定期的に確かめる**(取っているだけでは足りない) |
| 環境定義書・パラメータシート | IaC(docker-compose.yml、Kubernetes のマニフェスト)、manifest.json、ConfigMap、環境変数、環境 d1・s1・p1 | 環境ごとの設定値を残す | 設定を Excel ではなく**ファイル(コード)で持ち、そのまま適用する**。環境の差(台数・IP フィルタ・キャッシュ)は manifest の `environments` と kustomize のオーバーレイに書く |
| 移行設計・リリース手順書 | ローリング更新、ロールバック、readiness プローブ | 止めずに・安全に入れ替える | 夜間に止めて入れ替えるのではなく、**動かしたまま 1 台ずつ入れ替える** |
| セキュリティ設計・脆弱性診断 | WAF、レート制限、CSP、認可(IDOR)、秘密情報の管理 | 攻撃に備える | 診断を待たず、**入口で毎回ふるい落とす**仕組みと、アプリの書き方の両方で守る |
| ネットワーク設計(FW・LB) | CDN・WAF(cdn-waf)、Ingress とエンドポイント(ingress)、キャッシュ、IP フィルタ、CORS | 通り道と入口の制限 | 入口が 2 段になる。外側(CDN・WAF)で**キャッシュ**と攻撃の遮断、内側(エンドポイント)で**ホスト名ごとの振り分けと IP フィルタ**。画面と API は別のホスト名(別オリジン)なので CORS を決める |
| FW のアクセス制御リスト(社内からだけ通す) | エンドポイントの IP フィルタ(`BACKOFFICE_IP_ALLOWLIST`・`ipFilters.office`) | 送り元の IP で通す・断る | FW の機器ではなく**入口の設定ファイル**に書き、環境ごとに違う(d1・s1 はお店も社内だけ) |
| システム監視設計(ログ監視・性能監視) | 指標(Prometheus)・ログ(Loki)・トレース(OpenTelemetry・Tempo) | 異常を見つけ、原因を探す | 1 リクエストの道筋(トレース)を `trace_id` でログとつなぐ。CCv2 の案件では Dynatrace・SAP Cloud Logging(ログの画面は OpenSearch Dashboards)がこの役 |
| 性能要件(応答 3 秒以内など) | p95 応答時間、JS の予算(budgets)、SSR のタイムアウト | 速さの目標 | 平均ではなく**遅い方の 5% を見る**。ビルドの時点で重すぎる物を止める |
| 容量計画(サイジング) | 容量計画、メモリ上限(mem_limit / limits)、台数 | 必要な大きさを見積もる | 上限を**わざと決めて**、超えたら落として作り直す(OOMKilled) |

## 2. 同じもの(言葉が違うだけ)

- **非機能要求グレード ≒ SLO と RTO・RPO**。稼働率 99.9%、復旧時間、失ってよいデータの量。考え方は同じです。
- **基本設計・方式設計 ≒ 方式設計書**。層ごとの方針と、その理由と、採らなかった案。
- **総合試験 ≒ E2E テスト**。利用者の操作の流れで確かめる点は同じです。
- **障害報告書 ≒ ポストモーテム**。何が起き、なぜ起き、次にどうするか。

## 3. 増えたもの・変わったもの

| 新しく見えるもの | 何が変わったか |
| --- | --- |
| **SLO・SLI・エラーバジェット** | 稼働率を「契約書の数字」から「毎日測って使う予算」に変えた。予算が残っていれば新機能を出し、減っていれば直すことを優先する |
| **バーンレートのアラート** | 「エラーが 1 件出たら鳴らす」ではなく、「このままだと月の予算を 2 日で使い切る速さ」で鳴らす。鳴りすぎと見逃しを両方減らす |
| **WAF・レート制限** | インターネットに直接出すので、攻撃や連打が毎日来る。入口でふるい落とす |
| **CDN・キャッシュ** | 世界中から来る利用者に速く返し、アプリの負担を減らす。ただし「ためてはいけない物」をためると事故になる |
| **SSR・ハイドレーション** | 画面をブラウザで作る(SPA)ようになり、検索エンジンや最初の表示のために、サーバーでも作る必要が出た |
| **ローリング更新・readiness** | 何度もリリースするので、止めずに入れ替える必要がある |
| **IaC** | 環境を何度も作り直すので、手順書ではなくファイルで持つ |
| **オンコール・当番表** | 運用を別会社に渡さず、作ったチームが自分で見る形が増えた |
| **CSP** | 画面に外部のスクリプト(計測・広告・決済)を入れるので、読み込んでよい物を一覧で縛る |
| **ヘッドレス・CMS 駆動の描画** | 画面と API を分け、画面の並びは CMS のデータで決める。文言の差し替えにリリースが要らなくなる代わりに、「知らない部品が来たらどうするか」「キャッシュでいつ反映されるか」を決める必要が出た |
| **エンドポイントと IP フィルタ** | 画面・API・管理画面を別のホスト名に分け、入口ごとに誰を通すかを決める。管理画面を「外に出さない」をファイル 1 行で表す |
| **aspect・定期ジョブの見張り** | 同じアプリを役割ごとの台に分ける。画面を持たないバッチは止まっても気づかれないので、**最後に成功した時刻**で見張る |
| **トレース** | 部品が増えたので、1 リクエストがどこで遅くなったかを、ログの突き合わせではなく 1 本の道筋で見る |
| **manifest と環境 d1・s1・p1** | 構成を 1 枚の設計図に書き、環境の差だけを重ねる。「検証だけ違う」を意図した差に限る |

### CCv2 の案件で出てくる言葉との対応 {#ccv2-words}

CCv2(SAP Commerce Cloud)の案件の設計書や Cloud Portal の画面に出てくる言葉と、SIer の言葉、ラボの部品の対応です。ラボの部品は CCv2 の呼び方に合わせています(SAP の資料の文章ではなく、呼び方の対応だけを示します)。

| CCv2 の案件の言葉 | SIer の言葉に近いもの | ラボで触れる所 |
| --- | --- | --- |
| エンドポイント(Cloud Portal) | 公開 URL の一覧、LB の振り分け設定 | ingress のホスト名ごとの振り分け(www・api・backoffice)。[Ingress とエンドポイント](/exercises/20-nw-ingress-endpoints) |
| IP フィルタ | FW のアクセス制御リスト | backoffice の `BACKOFFICE_IP_ALLOWLIST`、manifest の `ipFilters` |
| aspect(api・backoffice・backgroundProcessing) | サーバーの役割分担(AP サーバー・管理サーバー・バッチサーバー) | 同じイメージを `ASPECT` で 3 役に切り替える |
| CronJob | バッチのジョブ定義、ジョブスケジューラ | worker の `stockImportJob`・`searchIndexJob` |
| OCC | 外部 IF の API 仕様 | `/occ/v2/samplestore/...` |
| JS Storefront / Composable Storefront | Web サーバー + 画面アプリ | storefront(Angular SSR)と CMS 駆動の描画。[CMS の JSON が画面になるまで](/exercises/21-headless-cms) |
| manifest.json とビルド | 環境構築手順書、デプロイ手順書、パラメータシート | [manifest.json](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/manifest.json) と `node tools/manifest/render.mjs` |
| 環境 d1・s1・p1 | 開発環境・検証環境・本番環境 | manifest の `environments`、本格版の `k8s/generated/envs/` |
| Dynatrace・SAP Cloud Logging | 性能監視・ログ監視の製品(ログの画面は OpenSearch Dashboards) | Prometheus・Grafana・Tempo(指標とトレース)、Loki(ログ) |
| 外部の CDN・WAF(お客さんが別に契約) | 前段の負荷分散装置・WAF 機器 | cdn-waf |

## 4. なぜ新しいものが出てきたのか

1. **クラウドで動かす**: サーバーを「買って置く」から「借りて、いつでも作り直す」になりました。台数を増やす・壊れたら作り直す・設定をファイルで持つ(IaC)が当たり前になり、インフラ・性能の文書が開発側に来ました。
2. **何度もリリースする**: 年に数回の大きなリリースから、週に何度もの小さなリリースになりました。止めずに入れ替える(ローリング更新)、自動のテスト(E2E)、「どれだけ失敗してよいか」の予算(エラーバジェット)が必要になりました。
3. **インターネットにそのまま出す**: 社内システムと違い、誰でも来ます。攻撃も連打も来ます。入口の守り(WAF・レート制限・CSP)と、入口での高速化(CDN)が必要になりました。

この 3 つを一言でまとめると、「**作った人が、動かし続ける責任まで持つようになった**」ということです。
このラボの演習は、その「動かし続ける」側の仕事を、小さく体験できるようにしたものです。

## 5. 自分の案件ではどこに書くか

SIer の文書体系をそのまま使っている案件でも、次のように割り振れば書く場所に困りません。

| このラボの設計書 | SIer の文書体系で書く場所の例 |
| --- | --- |
| [全体方式](/design/architecture/00-overall) | 基本設計書(方式設計)の総論、システム構成図 |
| [FE 方式](/design/architecture/01-frontend)・[BE 方式](/design/architecture/02-backend) | 基本設計書(アプリケーション方式) |
| [インフラ方式](/design/architecture/03-infrastructure)・[ネットワーク方式](/design/architecture/04-network) | 基盤設計書、ネットワーク設計書、パラメータシート |
| [SRE 方式](/design/architecture/05-sre) | 運用設計書(監視設計の章) |
| [QA 方式](/design/architecture/06-qa) | テスト計画書 |
| [性能方式](/design/architecture/07-performance) | 非機能要件定義書(性能)、性能試験計画書 |
| [障害対応方式](/design/architecture/08-incident-response) | 障害対応手順書、運用設計書(障害対応の章) |
| [DR 方式](/design/architecture/09-disaster-recovery) | バックアップ設計書、BCP |
| [セキュリティ方式](/design/architecture/10-security) | セキュリティ設計書 |

大事なのは文書の名前ではなく、**[必要なこと一覧](/guide/checklist) の各行が、どこかの文書のどこかの節に書いてあること**です。どこにも書いていない行が、事故の種になります。
