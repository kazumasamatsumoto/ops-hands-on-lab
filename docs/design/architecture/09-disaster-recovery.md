# DR 方式設計書(ラボ)

版: 2.0 / 親: [全体方式](/design/architecture/00-overall) / 対象: db(PostgreSQL)のバックアップと復元、作り直せる物(検索の索引など)

::: tip 3 行まとめ(この文書で決めたこと)
- 守るのは DB(商品・会員・注文・CMS のページ)だけ。指標・ログ・キャッシュ・検索の索引(Solr)は、失ってもよいか DB から作り直せる物として、バックアップしない。
- バックアップは `pg_dump` で DB を丸ごと 1 つの SQL ファイルに書き出す。復元は「全部成功するか、何も変えないか」のどちらかにする。
- 「取っている」だけでは足りないので、演習で実際に壊して戻し、戻るまでの時間(RTO)と失ったデータの量(RPO)を測る。
:::

## 0. 位置づけ {#s0}
全体方式の層分けのうち「データの層」を、失ったときにどう戻すかの観点で決めます。
配下: [D-DR-02 バックアップと復元](/design/detail/D-DR-02-backup-restore)。

## 1. 目的と範囲 {#s1}
- **含む**: 守る物と守らない物、バックアップの方式、復元の方式、RTO・RPO の測り方、訓練、作り直せる物(検索の索引)の戻し方。
- **含まない**: 別の拠点への切り替え、自動の定期バックアップ、バックアップの別の場所への保管(現場では要る。[必要なこと一覧](/guide/checklist))。

## 2. 前提 {#s2}
| 前提 | 内容 |
| --- | --- |
| データの置き場所 | 軽量版は Docker のボリューム `db-data`。本格版は StatefulSet `db`(Pod `db-0`、`postgres:17.11-alpine`)の PersistentVolumeClaim `data-db-0`(1Gi)。Pod を消してもデータは残るが、`k8s/down.sh` でクラスタごと消える |
| 消えるとき | `docker compose down -v` でボリュームごと消える(わざと消して練習できる) |
| 起動時の動き | api(`ASPECT=api`)はテーブルが空なら見本データを入れる。**空の DB に戻っただけでは、演習中に変えたデータ(backoffice で変えた価格・バナーなど)は戻らない** |
| 同じ DB を使う物 | api・backoffice・worker の 3 役とも同じ DB を読み書きする |

## 3. 全体像 {#s3}
| データ | 置き場所 | 失ったら | 方針 |
| --- | --- | --- | --- |
| 商品・会員・注文・CMS のページと部品 | db | 取り戻せない(お客さまの注文や、CMS で直した文言が消える) | **バックアップする** |
| ログイン中のトークン・backoffice のセッション | db | ログインし直せばよい | DB のバックアップに一緒に入るが、戻す必要はない |
| 検索の索引 | Solr(本格版。Pod の中の一時的な置き場所) | 次の `searchIndexJob`(60 秒ごと)で DB から作り直される | しない(作り直す) |
| 指標 | Prometheus(31 日で消える) | 過去のグラフが見えなくなるだけ | しない |
| ログ | Loki(7 日で消える) | 過去の調査ができなくなる | しない(現場では監査の要件を確かめる) |
| キャッシュ | cdn-waf(30 秒・画像は 1 日) | 次のリクエストで作り直される | しない |
| 設定・構成 | リポジトリ(manifest.json などのファイル) | リポジトリから作り直せる | Git が控え |

## 4. 決定事項 {#s4}
### 4.1 守る物を決める {#s4-1}
| 項目 | 内容 |
| --- | --- |
| 決定 | バックアップするのは DB だけ。ほかは「作り直せる」か「失ってもよい」 |
| 理由 | 全部を同じ重さで守ると、手間がかかって結局どれも続かない。ヘッドレスでは CMS のページも DB に入るので、商品と同じ重さで守る |

### 4.2 バックアップ {#s4-2}
| 項目 | 内容 |
| --- | --- |
| 決定 | `tools/backup.sh` で、db コンテナの中の `pg_dump` を使い、`backups/store-年月日-時分秒.sql` に書き出す。`--clean --if-exists` を付け、復元のときに「今あるテーブルを消してから作り直す」形にする。`--no-owner` で持ち主の情報を外す |
| 理由 | 1 つのファイルなので、中身を目で確かめられ、別の DB にも戻せる |
| 却下した案 | ボリュームのファイルをそのまま写す: DB が動いている最中に写すと、壊れた写しになることがある |
| 実物 | [backup.sh](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/backup.sh) |

### 4.3 復元 {#s4-3}
| 項目 | 内容 |
| --- | --- |
| 決定 | `tools/restore.sh [ファイル]` で `psql` に流し込む(省略すると一番新しいファイル)。`ON_ERROR_STOP=1`(途中でエラーが出たら止める)と `--single-transaction`(全部成功するか、何も変えないか)を付ける。戻したあと、cdn-waf のキャッシュが切れる(30 秒)まで古い画面が出ることがある |
| 理由 | 途中まで戻った中途半端な状態で「成功」と言わないため |
| 却下した案 | エラーを無視して最後まで流す: 一部のテーブルだけ古い、という一番分かりにくい状態になる |
| 実物 | [restore.sh](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/restore.sh) |

### 4.4 RTO と RPO を測る {#s4-4}
| 項目 | 内容 |
| --- | --- |
| 決定 | 演習で、壊した時刻・復元を始めた時刻・画面で確かめ終えた時刻・最後のバックアップの時刻を記録し、RTO と RPO を計算する |
| 理由 | 目標は測って初めて意味がある。「たぶん 30 分で戻せる」は目標ではない |

### 4.5 訓練 {#s4-5}
| 項目 | 内容 |
| --- | --- |
| 決定 | 復元は演習のたびに実際に行う。手順はスクリプト 2 本だけにして、誰でも同じ手順で戻せるようにする |
| 理由 | 戻し方を知っている人が 1 人だけだと、その人がいない日に戻せない |

### 4.6 作り直せる物(検索の索引) {#s4-6}
| 項目 | 内容 |
| --- | --- |
| 決定 | Solr の索引はバックアップしない。正本は DB で、worker の `searchIndexJob` が `CRON_INTERVAL_SECONDS`(60 秒)ごとに DB の全商品で作り直す。本格版の Solr は索引を Pod の中の一時的な置き場所(`emptyDir`)に置き、Pod が作り直されたら次のジョブで戻る(`k8s/platform/search.yaml`)。DB を復元したあとも、次のジョブで索引が DB に追いつく |
| 理由 | 作り直せる物までバックアップすると、手間と「どちらが正しいか」の迷いが増える。正本を 1 つ(DB)に決めておけば、戻すのは 1 か所で済む |
| 却下した案 | Solr のデータもバックアップする: DB と時点がずれて、復元後に検索と詳細で値が食い違う |
| 実物 | [aspects/worker.js](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/apps/api/src/aspects/worker.js)・[solr.js](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/apps/api/src/solr.js)・[k8s/platform/search.yaml](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/k8s/platform/search.yaml) |

## 5. 目標 {#s5}
| 項目 | 目標(ラボ) | 計算式 |
| --- | --- | --- |
| RTO(戻るまでの時間) | 10 分以内(演習で測る) | RTO = 画面で確かめ終えた時刻 − 壊れた(気づいた)時刻 |
| RPO(失ってよい量) | 最後のバックアップの時点まで | RPO = 壊れた時刻 − 最後にバックアップを取った時刻。例: 1 日 1 回なら最大 24 時間ぶんの注文を失う |
| 復元の成否 | 全部成功か、何も変えないか | `--single-transaction` |
| 索引が追いつくまで | 最大 60 秒 | `searchIndexJob` の間隔 |

::: info RPO を小さくするには
バックアップの間隔を短くするほど RPO は小さくなりますが、手間と置き場所が増えます。本番の DB では、変更の記録(WAL)を少しずつ別の場所に送り続けて、数分単位の RPO にする方法がよく使われます。ラボでは扱いません。
:::

## 8. レビュー観点 {#s8}
- [ ] 守る物と、守らない物(失ってもよい物・作り直せる物)が分けて書いてあるか
- [ ] 作り直せる物の「正本」と作り直し方が決まっているか
- [ ] RTO・RPO に計算式があり、実際に測った記録があるか
- [ ] 復元が「中途半端な成功」にならない作りか
- [ ] バックアップが本番と同じ場所だけに置かれていないか
- [ ] バックアップが止まっていないかを誰が・いつ確かめるか
