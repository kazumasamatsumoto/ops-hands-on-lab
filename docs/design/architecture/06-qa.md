# QA 方式設計書(ラボ)

版: 2.0 / 親: [全体方式](/design/architecture/00-overall) / 対象: E2E テスト・画面比較・守りの確認・ビルド時の検査・構成の食い違いの確認

::: tip 3 行まとめ(この文書で決めたこと)
- 主要な導線(トップ → 検索 → 商品詳細 → ログイン → 注文履歴 → 注文の詳細)を Playwright で自動でなぞり、画面の画像も前回と比べる。SSR で描かれたか・CORS と CSP に止められていないかも確かめる。
- 正常系だけでなく、「他人の注文が見えない」「攻撃の見本が 403 で止まる」も毎回確かめる。
- 重くなった画面(JS の予算超え)はビルドの時点で、manifest.json と compose・ingress の食い違いは `render.mjs --check` で止める。
:::

## 0. 位置づけ {#s0}
全体方式の「わざと壊すスイッチ」を使い、壊したときにテストが落ちること(= テストが効いていること)まで確かめます。
配下: [D-QA-04 E2E テスト](/design/detail/D-QA-04-e2e)。

## 1. 目的と範囲 {#s1}
- **含む**: テストの種類と担当、E2E の導線、画面比較、権限と守りの確認、ビルド時の検査、構成(manifest)の食い違いの確認。
- **含まない**: 単体テスト、外部の脆弱性診断、受入テスト(現場では要る。[必要なこと一覧](/guide/checklist))。

## 2. 前提 {#s2}
| 前提 | 内容 |
| --- | --- |
| 道具 | Playwright(Docker イメージ `mcr.microsoft.com/playwright:v1.63.0-noble` で動かす。PC に入れない) |
| 相手 | cdn-waf 経由。テストのコンテナは cdn-waf と同じネットワークの部屋(`--network container:...`)に入り、利用者と同じ `http://www.lab.localhost:18080` で開く |
| データ | 見本の会員 `alice`・`bob`(パスワード `password`)と見本の商品・注文。worker が在庫を 1 分ごとに少しずつ変えるので、在庫の表示は比べない |

## 3. 全体像 {#s3}
| 種類 | 何を確かめるか | 道具 | いつ |
| --- | --- | --- | --- |
| ビルド時の検査 | 最初に読む JS・CSS が 450kB 以下か | `ng build`(angular.json の budgets) | イメージを作るたび |
| 構成の食い違い | manifest.json と docker-compose.yml・ingress の設定が合っているか | `node tools/manifest/render.mjs --check` | manifest か compose を変えたとき |
| E2E テスト | 利用者の導線が端から端まで通るか | Playwright(`tools/e2e.sh`) | 変更のたび |
| 画面比較 | 見た目が前回から変わっていないか | Playwright のスクリーンショット比較 | 変更のたび |
| 権限の確認 | 他人の注文が見えないか | E2E の 1 本 | 変更のたび |
| 守りの確認 | 攻撃の見本が 403 で止まり、普通の検索は通るか | [tools/attack-samples.sh](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/attack-samples.sh) | cdn-waf の設定を変えたとき |
| 負荷試験 | どこまで耐えるか | k6([性能方式](/design/architecture/07-performance)) | 大きな変更の前 |

## 4. 決定事項 {#s4}
### 4.1 テストの種類 {#s4-1}
| 項目 | 内容 |
| --- | --- |
| 決定 | 上の表の 7 種類を持つ。権限の確認は「正常に見える」だけでなく「**見えてはいけない物が見えない**」を必ず入れる(`bob` でログインして `alice` の注文 `00001001` を開くと「注文を表示できませんでした」、合計が出ない) |
| 理由 | 認可の抜けは正常系のテストでは見つからない。いちばん多い事故の 1 つ。`tools/chaos.sh set idorBug=true` でこのテストが落ちることも確かめる |
| 却下した案 | 正常系だけ: 他人の注文が見える穴を本番に出す |
| 実物 | [tests/authz.spec.ts](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/e2e/tests/authz.spec.ts)・[apps/api/src/occ/orders.js](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/apps/api/src/occ/orders.js) |

### 4.2 E2E テスト {#s4-2}
| 項目 | 内容 |
| --- | --- |
| 決定 | 1 本の導線: トップ(応答ヘッダ `X-Render-Mode: ssr`、見出し「秋の文房具フェア」、CMS の `ProductCarouselComponent`)→ 検索(ノート)→ 商品詳細(`/p/100001`、価格、ブラウザが別オリジンの api を呼んだこと)→ ログイン(`alice`)→ 注文履歴 → 注文の詳細(合計)。最後にブラウザのコンソールに CSP・CORS のエラーが無いことを確かめる。別の 1 本で、無い商品(`/p/NO-SUCH-CODE`)が HTTP 404 になることを確かめる |
| 理由 | 「買い物の途中で行き止まりにならない」ことを、リリースのたびに機械で確かめる。SSR が壊れて CSR に逃げても画面は出るので、見た目だけでなくヘッダも見る。ヘッドレスでは CORS・CSP の設定漏れで「画面は出るがデータが来ない」が起きやすい |
| 却下した案 | 人が毎回手で確かめる: 忙しい日ほど省かれる |
| 実物 | [tests/journey.spec.ts](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/e2e/tests/journey.spec.ts)・[tools/e2e.sh](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/e2e.sh) |

### 4.3 画面比較 {#s4-3}
| 項目 | 内容 |
| --- | --- |
| 決定 | トップ・検索結果・商品詳細(`/p/100001`)の画面全体のスクリーンショットを基準画像として保存し、毎回の画像と比べる。毎回変わる部分(描画モードの表示、在庫の数・「在庫なし」)は隠してから比べる。基準の撮り直しは `tools/e2e.sh --update-snapshots` で、レビューで承認してから |
| 理由 | CSS の 1 行でボタンが画面外に出ても、機能のテストは通ってしまう。CMS 駆動の画面は、データの変更でも見た目が変わる |
| 実物 | [tests/visual.spec.ts](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/e2e/tests/visual.spec.ts) |

### 4.4 守りの確認 {#s4-4}
| 項目 | 内容 |
| --- | --- |
| 決定 | cdn-waf の設定(WAF の閾値・例外ルール)を変えたら、攻撃の見本 7 本(api の検索に 5 本、画面の検索に 2 本)が 403、普通の検索 2 本(api と画面)が 200 になることを確かめる。送り先はラボ(`www.lab.localhost`・`api.lab.localhost`)に固定し、`--resolve` で必ず 127.0.0.1 に向ける |
| 理由 | 誤遮断を直そうとして例外を広げすぎると、守りが外れる。直したあとで必ず両方向を確かめる |
| 実物 | [attack-samples.sh](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/attack-samples.sh) |

### 4.5 manifest と compose の食い違いを確かめる {#s4-5}
| 項目 | 内容 |
| --- | --- |
| 決定 | `node tools/manifest/render.mjs --check` で、manifest.json と、手で合わせている docker-compose.yml・ingress/default.conf.template を比べる。比べるのは: aspect ごとの `ASPECT` と環境変数、エンドポイントのホスト名 → 行き先、回数制限の場所、IP フィルタの範囲。食い違いがあれば一覧を出して失敗する |
| 理由 | 構成の正本は manifest.json だが、軽量版は手で合わせている。「本格版では IP フィルタが効くのに軽量版では効かない」のような、版による違いを見逃さない |
| 却下した案 | 目で見比べる: 行が多く、1 文字の違い(IP の範囲など)を見落とす |
| 実物 | [tools/manifest/render.mjs](https://github.com/kazumasamatsumoto/ops-hands-on-lab/blob/main/tools/manifest/render.mjs)(`check`) |

## 5. 目標 {#s5}
| 項目 | 目標 |
| --- | --- |
| 主要導線の E2E | 全部通る(1 つでも落ちたらリリースしない) |
| 画面比較 | 差分 0(意図した変更なら基準画像を更新し、レビューで承認する) |
| 権限の確認 | 他人の注文が見える件数 0 |
| 守りの確認 | 攻撃の見本 7/7 が 403、普通の検索 2/2 が 200 |
| JS の予算 | 450kB 以下(ビルドで強制) |
| 構成の食い違い | 0 件(`--check` が通る) |

## 8. レビュー観点 {#s8}
- [ ] 主要な導線(利用者が買い物を終えるまで)が E2E に入っているか
- [ ] 「見えてはいけない物が見えない」テストがあるか
- [ ] わざと壊したとき(スイッチを入れたとき)に、テストが本当に落ちるか
- [ ] 画面比較の基準画像を更新するときの承認の流れがあるか
- [ ] 守りの設定を変えたら、攻撃の見本と普通の入力の両方を流しているか
- [ ] 構成の正本(manifest)と実際に動かす定義の食い違いを、機械で確かめているか
