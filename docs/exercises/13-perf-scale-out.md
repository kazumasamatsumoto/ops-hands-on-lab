# 性能-2 台数を増やして耐える

::: info この演習について
- 所要時間: 約 20 分(負荷 1 分半 × 2 回を含む)
- 使うもの: 軽量版(docker compose)。k6。本格版(kind)があれば `kubectl scale` も
- 関係する設計書: [性能方式 4.5 台数を増やす](/design/architecture/07-performance#s4-5)・[インフラ方式](/design/architecture/03-infrastructure)・[D-PERF-05 負荷試験](/design/detail/D-PERF-05-load-test)・[D-INF-01 起動構成](/design/detail/D-INF-01-compose-and-k8s)
:::

[性能-1](./12-perf-load-test) で、web 1 台の限界を見たあとに進むと分かりやすいです。

## 1. この設計書はなぜ必要か

1 台で頑張るやり方(1 台を大きくする)には上限があり、しかもその 1 台が止まれば全部止まります。
「同じ物を何台も並べて、入口で振り分ける(スケールアウト)」ができる作りにしておかないと、混んだ日に打つ手がありません。

> **よくある事故**: テレビで紹介されるという連絡が前日に来ました。「サーバーを増やせば大丈夫」と思っていたら、アプリがログインの情報をサーバーのメモリに持っていたため、
> 2 台にするとログインしたはずのお客様が「ログインしてください」と何度も言われる作りでした。結局 1 台のまま当日を迎え、放送の 5 分後に落ちました。

何台から始めて、何を見て何台まで増やすか。増やせる作りになっているか(台ごとに覚えている物が無いか)。これを性能とインフラの方式設計書に書きます。

## 2. 何をやっているのか

軽量版では `docker compose up -d --scale web=3` で web を 3 台に増やせます。edge は「web」という名前で振り分けるので、Docker が 3 台の住所を返し、edge が順番に配ります。
同じ負荷(400 人、1 分)を、web 1 台のときと 3 台のときでかけ、件数と p95 を比べます。
入口の作り置き(キャッシュ)とレート制限は、試験の間だけ切ります(web の力を測るため)。

たとえ: **スーパーのレジを 1 台から 3 台に増やす** ことです。行列は短くなります。ただし、レジ係が「このお客様のポイントカードは私が預かっている」という働き方(台ごとに覚えている物)だと、別のレジに並べません。
サンプルストアの web は、ログインの印をブラウザ側(sessionStorage)に持つので、どの台に当たってもかまいません。

## 3. まず触ってみる

1. **試験のために、入口のキャッシュとレート制限を外す**(試験が終わったら必ず戻します)。

   ```bash
   EDGE_CACHE=off EDGE_GLOBAL_RATE=10000r/s docker compose up -d edge
   docker compose ps edge        # (healthy) を待つ
   ```

2. **web 1 台のまま、400 人で 1 分かける**(20 秒で 400 人まで増やし、60 秒続け、10 秒で片付け)。

   ```bash
   tools/k6.sh ramp.js -e TARGET=page --stage 20s:400 --stage 60s:400 --stage 10s:0 2>&1 \
     | grep -E 'http_req_duration\.\.|http_req_failed|http_reqs\.'
   ```

3. **web を 3 台に増やす**。

   ```bash
   docker compose up -d --scale web=3 --no-recreate web
   docker compose ps web
   ```

   3 台とも `(healthy)` になったら、10 秒ほど待ちます(edge が名前を調べ直すのを待つため)。

4. **同じ負荷をもう一度かける**。

   ```bash
   tools/k6.sh ramp.js -e TARGET=page --stage 20s:400 --stage 60s:400 --stage 10s:0 2>&1 \
     | grep -E 'http_req_duration\.\.|http_req_failed|http_reqs\.'
   ```

5. **3 台に均等に配られたか数える**。

   ```bash
   for c in 1 2 3; do printf 'lab-web-%s: ' $c; docker logs lab-web-$c --since 2m 2>&1 | grep -c '"route":"/products/:id"'; done
   ```

### 本格版では

本格版(kind)では、台数を 1 行で変えられます。詳しくは `k8s/README.md` を見てください(台数を自動で増減する HPA は入れていません。理由も README にあります)。

```bash
kubectl -n lab get pods -l app=web -w          # 別のターミナルで、Pod が増える様子を見る
kubectl -n lab scale deploy/web --replicas=4   # 4 台に増やす
kubectl -n lab scale deploy/web --replicas=2   # 元の 2 台に戻す
```

## 4. 何が見えたら成功か

**手順 2 と 4 の比較**(同じ 400 人・同じ時間。実測)

| | web 1 台 | web 3 台 |
| --- | --- | --- |
| 件数 / 秒 | 425 | 560 |
| 真ん中の人の待ち時間(med) | 0.313 秒 | 0.075 秒 |
| p95 | 0.460 秒 | 0.255 秒 |
| 失敗 | 0% | 0% |

```text
web 1 台:
    http_req_duration..............: avg=283.55ms min=5.64ms   med=313.3ms  max=644.47ms p(90)=382.36ms p(95)=460.49ms
    http_req_failed................: 0.00%  0 out of 38395
    http_reqs......................: 38395  424.767736/s

web 3 台:
    http_req_duration..............: avg=93.68ms  min=5.85ms   med=74.57ms  max=543.25ms p(90)=193.42ms p(95)=254.75ms
    http_req_failed................: 0.00%  0 out of 50621
    http_reqs......................: 50621  560.263997/s
```

待ち時間は大きく減りました。一方、件数は 3 倍ではなく 1.3 倍です。これは試験の作りのためです。
400 人それぞれが「リクエスト → 0.5 秒考える → リクエスト」を繰り返すので、件数は **400 ÷(0.5 秒 + 待ち時間)** より多くはなりません。
待ち時間が 0.09 秒まで縮めば上限は約 670 件 / 秒で、もう「お客様の数」の方が先に限界です。**もっと件数を出すには、客役を増やす** 必要があります(台数を増やすと、次の細い所が見えてくる、ということでもあります)。

**手順 5**: 3 台に、ほぼ 3 分の 1 ずつ配られています。

```text
lab-web-1: 17139
lab-web-2: 16755
lab-web-3: 16813
```

::: warning 試験の途中で見つかった「入口の限界」
最初にこの演習を作ったとき、web 1 台の試験で **6.77% が 502** になりました。edge のログには次の行が並んでいました。

```text
[crit] connect() to 172.30.89.11:4000 failed (99: Address not available) while connecting to upstream
```

edge は奥へのリクエストのたびに新しい接続を作り、閉じた接続の後始末(TIME_WAIT)の間は「つなぎ口の番号」が使えません。1 秒に 400 件を超えると番号が足りなくなったのです。
アプリではなく **入口のつなぎ方** が限界でした。今は `docker-compose.yml` の edge に `sysctls`(使える番号を広げ、後始末中の番号を使い回す設定)を入れて直してあります。
本番なら、奥との接続を使い回す(keepalive)設定も検討します。負荷試験は、こういう「思ってもみなかった細い所」を見つけるためにやるのです。
:::

::: tip 台数を増やしたら、指標の集め方も変わる
Prometheus は `web:4000` という名前で指標を集めているので、3 台にすると毎回どれか 1 台の数字しか取れません(3 台の合計にならない)。
本格版(Kubernetes)では、Prometheus が Pod を 1 つずつ見つけて集めます。台数を増やす設計では、監視の設計も一緒に見直します。
:::

## 5. ここで覚える言葉

| 言葉 | 一言でいうと | たとえ | この演習で見たもの |
| --- | --- | --- | --- |
| スケールアウト | 同じ物の台数を増やして、仕事を分ける | レジを 1 台から 3 台に | `--scale web=3` |
| スケールアップ | 1 台を大きく(速く)する | 1 台のレジ係を熟練の人にする | (この演習では使わない) |
| 振り分け(ロードバランス) | 来た仕事を複数の台に配る | 「空いているレジへどうぞ」の案内係 | 3 台に 17,139 / 16,755 / 16,813 件 |
| ステートレス | 台ごとに覚えている物が無い作り | どのレジでもポイントカードが使える | ログインの印はブラウザ側に持つ |
| レプリカ | 同じアプリの台数 | 同じ仕事をするレジの数 | 本格版の `--replicas=4` |
| HPA(自動の台数調整) | 負荷に合わせて台数を自動で増減する | 行列の長さで自動的にレジを開ける | 本格版には入れていない |
| 容量計画(キャパシティプランニング) | ピークに何台要るかを見積もること | 年末のレジ係のシフト表 | 1 台 425 件 / 秒 → ピーク○件なら○台 |

## 6. 設計書ではここに書く

- **[性能方式 4.5 台数を増やす](/design/architecture/07-performance#s4-5)**: 「web は最低 2 台、最大○台。p95 が 0.5 秒を超えそうなら増やす」「台ごとに覚えている物を持たない(ログインの印はブラウザ、データは DB)」と書きます。
- **[性能方式 5 目標](/design/architecture/07-performance#s5)**: 「1 台で○件 / 秒(負荷試験の結果)、ピーク○件 / 秒なので○台 + 予備 1 台」の計算。
- **[インフラ方式 4.3 メモリの上限](/design/architecture/03-infrastructure#s4-3)**: 台数 × 1 台のメモリ上限が、置き場所(サーバー)に収まるか。
- **[D-INF-01 起動構成 4.3 本格版の Pod](/design/detail/D-INF-01-compose-and-k8s#s4-3)**(一般のカタログでは D-INF-01): レプリカ数、台数を変える手順とコマンド。
- **[D-PERF-05 負荷試験 4.4 記録する物](/design/detail/D-PERF-05-load-test#s4-4)**(一般のカタログでは D-PERF-05): 台数ごとの件数と p95 の表(この演習の表)と、試験の間だけ変えた設定(キャッシュ OFF、レート制限の緩和)。

## 7. レビューで聞く質問

- 「web や api を 2 台以上にしたとき、台ごとに覚えている物(ログイン状態、アップロード中のファイルなど)はありませんか。」
- 「1 台で何件 / 秒さばけると測りましたか。その数字から、ピークに何台要ると計算しましたか。」
- 「台数を増やす判断は誰が、何の数字を見てしますか。どれくらいの時間で増やせますか。」
- 「台数を増やしたとき、DB の接続数や入口(ロードバランサ)など、次に詰まる所はどこですか。」
- 「台数を増やしても、監視(指標やログ)は全部の台のぶんを集められますか。」

## 8. 片付け

web を 1 台に戻し、edge のキャッシュとレート制限を既定に戻します。

```bash
docker compose up -d --scale web=1 web
docker compose up -d edge                               # EDGE_CACHE=on、EDGE_GLOBAL_RATE=20r/s に戻る
docker compose exec -T edge printenv EDGE_CACHE EDGE_GLOBAL_RATE
docker compose ps                                       # web が 1 台だけならよい
```
