# SRE-1 SLI を測って SLO と比べる

::: info この演習について
- 所要時間: 約 25 分(負荷をかける 1 分を含む)
- 使うもの: 軽量版(docker compose)。k6(`tools/k6.sh`)、Prometheus(http://localhost:19090)、Grafana(http://localhost:13000)
- 関係する設計書: [SRE 方式 4.1 SLI](/design/architecture/05-sre#s4-1)・[SRE 方式 4.2 SLO とエラーバジェット](/design/architecture/05-sre#s4-2)・[D-SRE-02 SLO とバーンレートのアラート](/design/detail/D-SRE-02-slo-burn-rate)
:::

## 1. この設計書はなぜ必要か

「システムは正常ですか?」と聞かれて、「サーバーは動いています」「CPU は 30% です」と答えていませんか。
お客様にとって大事なのは、**頼んだことが、ちゃんと、速く返ってきたか** だけです。

> **よくある事故**: 月曜の朝、発注元から「先週末、注文ボタンを押してもエラーになるとお客様から苦情が来ている」と連絡がありました。
> 監視の画面は、サーバーの CPU もメモリもずっと緑。調べると、注文の API だけが 50 回に 1 回エラーを返していました。
> さらに困ったのは、「50 回に 1 回は許される範囲なのか」を誰も答えられず、発注元と揉めたことです。目標の数字を、どこにも書いていなかったのです。

お客様の体験を数字にしたもの(SLI)と、その目標(SLO)を先に決めて合意しておけば、「今は良いのか悪いのか」を誰でも同じ物差しで言えます。これを SRE の方式設計書に書きます。

## 2. 何をやっているのか

サンプルストアでは、api と web が「リクエストの数(状態コード別)」と「かかった時間」を数え、Prometheus が 5 秒ごとに集めています。
Prometheus の **記録ルール**(`observability/prometheus/rules/slo-recording.yml`)が、そこから次の 2 つの SLI を計算し続けています。

- **成功率** = 5xx(サーバーの失敗)以外の件数 ÷ 全体の件数
- **p95 応答時間** = 100 件を速い順に並べたとき、95 件目の時間

SLO(目標)は「1 か月の成功率 99.9%」です。演習では、api にわざと 2% のエラーを混ぜ、k6 で 1 分間お客様のまねをさせ、**Prometheus の生の数字から SLI を手で計算し**、記録ルールと Grafana の数字と見比べます。

たとえ: **SLI は「健康診断の検査値」、SLO は「基準値」** です。「血圧 125」(SLI)だけでは良いか悪いか分かりませんが、「130 未満なら正常」(SLO)があれば判断できます。
そして大事なのは「本人が困ること」を測ることです。CPU の使用率は、たとえるなら「心臓の動いた回数」で、本人の元気さとは別物です。

## 3. まず触ってみる

1. **数え直しやすくするため、api を再起動して数を 0 にする**(数え札は api のメモリの中にあるので、再起動で 0 に戻ります)。

   ```bash
   docker compose restart api
   docker compose ps api        # (healthy) を待つ
   ```

   ただし Prometheus の「直近 5 分」の計算には、再起動の前に来たリクエストも入ります。[ネットワーク-1](./07-nw-cache) で `latencyMs=300` を入れてから 5 分たっていないときは、5 分待ってから次へ進んでください(待たないと、手順 5 の p95 が 0.3 秒前後に引っぱられます)。

2. **api に 2% のエラーを混ぜ、1 分間お客様のまねをする**。edge のキャッシュに吸収されないよう、ここでは api に直接かけます(`BASE_URL=http://api:3001`)。

   ```bash
   tools/chaos.sh set errorRate=0.02
   BASE_URL=http://api:3001 tools/k6.sh browse.js -e VUS=10 -e DURATION=1m -e PAGES=0
   ```

   k6 の最後に出る `http_req_failed`(失敗の割合)と `p(95)` を控えておきます。

3. **Prometheus で「生の数」を見る**。http://localhost:19090 の「Query」に次を貼って「Execute」します(`curl` で聞いても同じです)。

   ```text
   sum by (status) (http_requests_total{job="api",route!~"/metrics|/healthz|/readyz|/admin/.*|unmatched"})
   ```

   ```text
   sum by (le) (http_request_duration_seconds_bucket{job="api",route!~"/metrics|/healthz|/readyz|/admin/.*|unmatched"})
   ```

   `route!~...` は、「見守り用の URL(`/metrics` など)は数えない」という意味です。お客様の体験と関係ないからです。

4. **手で計算する**(下の「何が見えたら成功か」に計算のしかたがあります)。

5. **記録ルールの答えと比べる**。

   ```text
   job:sli_success:ratio_rate5m{job="api"}
   job:http_request_duration_seconds:p95_rate5m{job="api"}
   job:slo_error_budget_remaining:ratio30d{job="api"}
   ```

6. **Grafana で見る**。http://localhost:13000 を開くと、ホームが「サンプルストア SLO」です。いちばん上の 4 つの枠(成功率・p95・エラーバジェットの残り・バーンレート)には、それぞれ `api` と `web` の 2 つの数字が名前付きで並びます。この演習では `api` の方を見ます。

## 4. 何が見えたら成功か

**手順 2**: k6 から見て、398 回中 10 回が失敗(2.51%)、p95 は 4.31ms。SLO の基準(k6 の合格条件 1% 未満)を超えたので、k6 自身も「基準を超えた」と言っています。

```text
http_req_duration..............: avg=3.03ms min=436µs med=2.86ms max=23.33ms p(90)=3.56ms p(95)=4.31ms
http_req_failed................: 2.51%  10 out of 398
http_reqs......................: 398    6.407034/s
level=error msg="thresholds on metrics 'http_req_failed' have been crossed"
```

**手順 3**: Prometheus の生の数(実測)。

```text
{status="200"}  388
{status="500"}  10

{le="0.005"}  389      ← 0.005 秒(5ms)以内に終わった件数
{le="0.01"}   390      ← 10ms 以内
{le="0.025"}  398      ← 25ms 以内(ここで全部)
...
{le="+Inf"}   398
```

**手順 4: 手で計算する**

- **成功率** = 5xx 以外 ÷ 全体 = 388 ÷ (388 + 10) = 388 ÷ 398 = **0.9749(97.49%)**
- **SLO と比べる**: 目標 99.9% に対して 97.49%。失敗の割合は 2.51% で、許される 0.1% の **約 25 倍**。
- **p95**: 全体 398 件の 95% は 378.1 件目。5ms 以内に 389 件が入っているので、p95 は 0〜5ms の間にあります。
  Prometheus はこの箱の中を「均等に並んでいる」とみなして、5ms × 378.1 ÷ 389 = **4.86ms** と見積もります。

**手順 5**: 記録ルールの答え(実測)。

```text
job:sli_success:ratio_rate5m{job="api"}                  0.9810
job:http_request_duration_seconds:p95_rate5m{job="api"}  0.004864     ← 手計算の 4.86ms と一致
job:slo_error_budget_remaining:ratio30d{job="api"}       -15.68
```

成功率が手計算(97.49%)より少し良い 98.10% になっているのは、記録ルールが「直近 5 分を 1 秒あたりに直して」計算するためです(途中から現れた 500 の数え札は、最初の 1 件ぶんが計算に入らないなど、短い時間だと少しずれます)。
長い時間で見れば手計算とそろいます。「数字の出し方を設計書に書いておく」ことが大事な理由がここにあります。

エラーバジェットの残り −15.68 は、「1 か月で失敗してよい量(0.1%)の、約 16.7 倍をもう使った」という意味です(1 − 0.01668 ÷ 0.001)。

**手順 6**: Grafana の上の 4 つの枠の `api` の数字(実測の画面の例): 成功率 **98.15%**(赤)、p95 **4.86 ms**(緑)、エラーバジェットの残り **−1581.7%**(赤)、バーンレート(1 時間窓)**16.8**(赤)。
「速さは合格、成功率は不合格」と、ひと目で分かります。

## 5. ここで覚える言葉

| 言葉 | 一言でいうと | たとえ | この演習で見たもの |
| --- | --- | --- | --- |
| SLI | お客様の体験を表す数字 | 健康診断の検査値 | 成功率 388 ÷ 398、p95 4.86ms |
| SLO | SLI の目標 | 検査値の基準値 | 「1 か月の成功率 99.9%」 |
| SLA | お客様との契約で約束する値(破ると返金など) | 保険の約款 | ラボには無い(SLO は SLA より厳しめに置く) |
| エラーバジェット | 目標の範囲で「失敗してよい量」 | 1 か月のお小遣い | 残り −15.68(使いすぎ) |
| p95 | 100 人中 95 人目の待ち時間 | 行列の遅い方から 5 人目 | `{le="0.005"} 389` から 4.86ms |
| ヒストグラム | 「何秒以内が何件」を箱ごとに数えたもの | 身長を 5cm ごとに数えた表 | `http_request_duration_seconds_bucket` |
| 記録ルール | よく使う計算を先にして名前を付けておく | 帳簿の小計欄 | `job:sli_success:ratio_rate5m` |
| PromQL | Prometheus に数字を聞く書き方 | 表計算の関数 | `sum by (status) (http_requests_total{...})` |

## 6. 設計書ではここに書く

- **[SRE 方式 4.1 SLI: 何を測るか](/design/architecture/05-sre#s4-1)**:
  「成功率 = 5xx 以外 ÷ 全体。見守り用の URL は数えない」「速さ = p95。平均は使わない(遅い 5% の人が隠れるため)」と、**式と、数えない物** まで書きます。
- **[SRE 方式 4.2 SLO とエラーバジェット](/design/architecture/05-sre#s4-2)**: 「1 か月の成功率 99.9%(= 失敗してよいのは 0.1%。全部止まるなら約 43 分)」「バジェットを使い切ったら、新しい機能のリリースを止めて直すことを優先する」。
- **[SRE 方式 4.6 ダッシュボード](/design/architecture/05-sre#s4-6)**: いちばん上に置く 4 つの数字と、その色の基準。
- **[全体方式 5 目標](/design/architecture/00-overall#s5)**: 発注元と合意した SLO の数字。
- **[D-SRE-02 SLO とバーンレートのアラート](/design/detail/D-SRE-02-slo-burn-rate)**(一般のカタログでは D-SRE-02): 記録ルールの名前と PromQL の式をそのまま書き、「手で確かめるときの PromQL」も書いておきます。

## 7. レビューで聞く質問

- 「このサービスの SLI は何ですか。お客様が困ったときに、その数字は必ず悪くなりますか。」
- 「成功率の分母と分子に、何を入れて何を外していますか(見守り用の URL、4xx など)。」
- 「速さの目標は、平均ではなく p95 や p99 で書いていますか。」
- 「SLO の数字は、発注元(業務の担当)と合意したものですか。いつ見直しますか。」
- 「エラーバジェットを使い切ったら、誰が何を決めますか(リリースを止める、など)。」
- 「ダッシュボードのこの数字を、Prometheus の生の数から手で計算し直せますか。」

## 8. 片付け

```bash
tools/chaos.sh reset          # errorRate を 0 に戻す
```

エラーバジェットの残りは「起動してからの全期間」で計算しているので、マイナスのまましばらく残ります。まっさらに戻したいときは、最後に `docker compose down -v` で指標のデータごと消します(ほかの演習の記録も消えます)。
