# 性能-1 負荷試験で限界を見る

::: info この演習について
- 所要時間: 約 30 分(負荷をかける時間 5 分 + 3 分を含む)
- 使うもの: 軽量版(docker compose)。k6(`tools/k6.sh`)、Prometheus(http://localhost:19090)、Grafana(http://localhost:13000)
- 関係する設計書: [性能方式 4.1 速さの目標](/design/architecture/07-performance#s4-1)・[性能方式 4.4 負荷試験](/design/architecture/07-performance#s4-4)・[D-PERF-05 負荷試験](/design/detail/D-PERF-05-load-test)
:::

## 1. この設計書はなぜ必要か

「何人まで耐えられますか?」に、数字と根拠で答えられないまま本番を迎えると、限界は **お客様が一番多い日** に見つかります。

> **よくある事故**: 年末セールの初日、朝 10 時の開始と同時にサイトが真っ白になりました。
> 負荷試験は「やった」ことになっていましたが、中身は「1 人で 100 回、商品一覧を開いて平均 0.3 秒だった」というものでした。
> 本番では何千人が同時に、商品詳細・検索・ログインを混ぜて使いました。しかも試験の合格の基準は「平均」だけで、失敗の割合を見ていませんでした。

どんな使われ方を・何人ぶん・どれくらいの時間かけて・何を見て合格とするか。これを性能の方式設計書と負荷試験の詳細設計書に書きます。

## 2. 何をやっているのか

k6(負荷をかける道具)が「仮想の利用者(VU)」を何人も作り、同時にリクエストを送ります。`tools/k6/ramp.js` は人数を段階的に増やす試験(ステップ負荷)です。
この演習では 2 回試します。

1. **いつもの入口(edge)経由で**: edge には「同じ IP から 1 秒 20 回まで」のレート制限があるので、k6 1 台から強くかけると、アプリの前に入口で止まります。
2. **入口を通さず web に直接**: 商品詳細の画面(サーバーで描画する = 重い処理)に、100 → 200 → 400 人と増やし、**件数が伸びなくなり、待ち時間が延び始める所(限界)** を探します。

たとえ: **ラーメン屋の行列** です。お客様(VU)を増やしていくと、最初は「来た分だけさばける」のに、ある所から厨房(サーバー)が追いつかず、さばける数は増えないのに待ち時間だけが延びます。そこが限界です。
なお、店の前の整理係(edge のレート制限)が「お 1 人様 1 秒に 20 回まで」と止めていると、厨房の限界を測る前に整理係で止まってしまいます。

## 3. まず触ってみる

1. **edge 経由で段階的に負荷をかける**(5 分半かかります)。その間、Grafana の「サンプルストア SLO」を開いておきます。

   ```bash
   tools/k6.sh ramp.js
   ```

2. **結果を読む**。最後にまとめが出ます。`http_req_failed`(失敗の割合)と、合格の基準(`THRESHOLDS`)を見比べてください。

3. **レート制限を避けて、web(画面)の限界を見る**。edge を通さず、Docker のネットワークの中から web(`http://web:4000`)に直接かけます。
   人数は `--stage 時間:人数` で上書きできます(ここでは 30 秒ずつ 100 → 200 → 400 人)。3 分かかります。

   ```bash
   BASE_URL=http://web:4000 tools/k6.sh ramp.js -e TARGET=page \
     --stage 30s:100 --stage 30s:100 --stage 30s:200 --stage 30s:200 --stage 30s:400 --stage 30s:400
   ```

4. **走っている間、30 秒ごとに Prometheus で数字を見る**。http://localhost:19090 の「Query」で、次の 3 つを実行します(Graph の表示にすると推移が見えます)。

   ```text
   sum(rate(http_requests_total{job="web",route="/products/:id"}[30s]))
   histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{job="web",route="/products/:id"}[30s])))
   rate(process_cpu_seconds_total{job="web"}[30s])
   ```

   上から「1 秒あたりの件数」「p95 の待ち時間(秒)」「web が使った CPU(1.0 = CPU 1 個ぶん)」です。

5. **メモリも見る**。

   ```bash
   docker stats --no-stream --format '{{.Name}} {{.CPUPerc}} {{.MemUsage}}' | grep lab-
   ```

## 4. 何が見えたら成功か

**手順 1〜2(edge 経由)**: 13,293 回のうち 8,436 回(63%)が 429(レート制限)。それなのに k6 の判定は **合格(✓)** です。
`ramp.js` の合格の基準が「p95 が 1 秒未満」だけで、失敗の割合を見ていないからです。**基準の決め方しだいで、ひどい結果でも合格になる** 良い見本です。

```text
  █ THRESHOLDS
    http_req_duration
    ✓ 'p(95)<1000' p(95)=11.54ms

    ✗ 200(成功)
      ↳  36% — ✓ 4857 / ✗ 8436
    ✗ 429 ではない(レート制限に当たっていない)
      ↳  36% — ✓ 4857 / ✗ 8436
    ✓ 5xx ではない

    http_req_failed................: 63.46% 8436 out of 13293
    http_reqs......................: 13293  44.258007/s
```

1 台の k6 は 1 つの IP なので、入口から見ると「1 人のお客様がものすごい速さで連打している」のと同じです。本物のお客様は何千もの別々の IP から来ます。
だから **アプリの限界を測るときは入口のレート制限を避ける**(奥に直接かける、試験のときだけ制限を緩める、k6 を何台にも分ける)工夫が要ります。どれを選んだかも試験の記録に書きます。

**手順 3〜4(web に直接)**: 30 秒ごとに見た数字(実測)。

| 経過 | 人数(VU) | 件数 / 秒 | p95 | web の CPU |
| --- | --- | --- | --- | --- |
| +60 秒 | 100 | 161 | 0.229 秒 | 0.40 |
| +120 秒 | 200 | 309 | 0.240 秒 | 0.70 |
| +150 秒 | 400 に増加中 | 458 | 0.315 秒 | 0.99 |
| +180 秒 | 400 | 537 | 0.467 秒 | 1.13 |

(参考: 同じ web に 5 → 20 → 50 人でかけたときは、9.6 / 36 / 86 件で p95 は 0.05〜0.10 秒でした。)

人数を 200 → 400 と **2 倍** にしても、件数は 309 → 537 と **1.7 倍** にしか増えず、p95 は 0.24 → 0.47 秒と **ほぼ 2 倍** に延びました。
web の CPU は 1.0(CPU 1 個ぶん)を超えています。Node.js は画面を組み立てる計算を 1 つの CPU でこなすので、ここがこの web 1 台の限界に近い所です。

k6 のまとめ(3 分全体):

```text
    ✓ 'p(95)<1000' p(95)=332.46ms
    http_req_duration..............: avg=171.09ms min=4.37ms   med=157.68ms max=451.11ms p(90)=305.29ms p(95)=332.46ms
    http_req_failed................: 0.00%  0 out of 53697
    http_reqs......................: 53697  297.49563/s
```

**手順 5**: 負荷のあとの web のメモリは 252MiB(上限 384MiB)。上限にはまだ余裕があり、先に限界に来たのは CPU だと分かります。

```text
lab-web-1 0.43% 252.3MiB / 384MiB
lab-api-1 0.45% 59.81MiB / 256MiB
```

::: tip p95 の数字が「0.1」「0.25」付近に張り付いて見えるとき
p95 は「何秒以内が何件」の箱(0.05 / 0.1 / 0.25 / 0.5 秒 …)から見積もった値です。箱の境目の近くでは粗くなります。細かく知りたいときは、k6 が直接測った `p(95)` と見比べます。
:::

## 5. ここで覚える言葉

| 言葉 | 一言でいうと | たとえ | この演習で見たもの |
| --- | --- | --- | --- |
| 負荷試験 | たくさんの利用者のまねをして、速さと限界を測る | 開店前に大勢の客役を呼んでリハーサル | `tools/k6.sh ramp.js` |
| VU(仮想の利用者) | k6 が作るお客様役 1 人 | 客役のアルバイト 1 人 | 100 → 200 → 400 人 |
| ステップ負荷 | 人数を段階的に増やす試験 | 客役を 10 分ごとに増やす | `--stage 30s:100 ...` |
| スループット | 1 秒にさばけた件数 | 1 分に出せたラーメンの杯数 | 309 → 537 件 / 秒 |
| レイテンシ(待ち時間)と p95 | 返事までの時間。p95 は 100 人中 95 人目 | 注文してから出てくるまで | 0.24 → 0.47 秒 |
| しきい値(合格の基準) | これを満たさないと不合格、という線 | 「15 分以上待たせたら失敗」の決まり | p95 だけで失敗率を見ず、63% 失敗でも合格 |
| レート制限 | 同じ相手からの回数を制限する | 整理係の「お 1 人様 1 秒 20 回まで」 | edge 経由で 429 が 63% |
| ボトルネック | 全体の速さを決めている、一番細い所 | 厨房のコンロの数 | web の CPU が 1.0 を超えた |

## 6. 設計書ではここに書く

## 7. レビューで聞く質問

- 「負荷試験の合格の基準に、失敗の割合は入っていますか。平均ではなく p95 で見ていますか。」
- 「試験の使われ方(どの画面をどの割合で)は、本番の予想とどう対応していますか。根拠は何ですか。」
- 「入口のレート制限や CDN のキャッシュは、試験のときどう扱いましたか。本番と違う所はどこですか。」
- 「限界(件数が伸びず待ち時間だけが延びる所)は何件 / 秒でしたか。そのとき、どこ(CPU・メモリ・DB)が詰まっていましたか。」
- 「本番のピークに対して、どれくらい余裕がありますか。足りないときは何台に増やしますか。」

## 8. 片付け

この演習では設定を変えていません。k6 はコマンドが終われば消えます。

```bash
docker ps --format '{{.Image}}' | grep -c grafana/k6     # 0 なら k6 は残っていない
tools/chaos.sh status                                    # すべて既定値のままならよい
```
